# ТЗ: командный таск-менеджер

Версия 0.4 от 10 ноября 2026. Целевое ТЗ полной системы.

Текущий объём первой разработки выделен в [MVP.md](MVP.md). Для MVP используется локальный Supabase на компьютере разработчика; облачный проект не требуется. Администраторы, подтверждение `done`, напоминания, сайт и Mini App реализуются следующими этапами. Требования ниже описывают полную систему и не означают, что всё входит в MVP.

## 1. Цель и порядок разработки

Система для команды до 10 человек. Сначала реализуются база Supabase и Telegram-бот, затем единое веб-приложение, доступное как Telegram Mini App и как сайт на VPS Hostinger. Все интерфейсы работают с одной базой и общим серверным API.

Этапы: согласование ТЗ → создание проекта и схемы Supabase → серверная логика и бот → приёмка полного сценария Telegram → Supabase → веб-приложение и Mini App → публикация сайта.

Имеется бот Telegram и VPS Hostinger с SSH. Проекта Supabase и домена пока нет. Характеристики VPS, способ запуска приложений и адрес для HTTPS уточняются при подготовке развёртывания.

## 2. Подтверждённые требования

- Пользователь видит только задачи, в которых он исполнитель; администратор видит все задачи команды.
- Пользователь сам создаёт задачу, по умолчанию становится её исполнителем и указывает дедлайн.
- Нужны проекты/направления и несколько исполнителей у одной задачи.
- Ответственными за задачу являются один или несколько администраторов. Наблюдатели не нужны.
- Поля «Важная» и «Быстрая» — независимые флаги.
- Дата занесения устанавливается автоматически; интерфейс показывает календарный день создания.
- Результат может содержать текст, ссылки и файлы.
- Бот работает в личных сообщениях. Приоритет — создание через кнопки. Свободный ввод текста планируется после базового сценария; голосовые не входят в первую версию.
- Статусы: «Новая», «В работе», «На проверке» (`review`), «Готово» (`done`), «Отменена».
- Пользователь прикладывает обязательный результат и может продвинуть задачу максимум до `review`. Выполнение подтверждает администратор (Илья), переводя задачу из `review` в `done`. Постановщик без роли администратора не может подтверждать выполнение. Подтверждение постановщика дополнительно к решению администратора не требуется.
- Напоминание отправляется в личный Telegram в день дедлайна. По просроченным задачам нужна ежедневная сводка.
- Эскалации руководителю, тихие часы и индивидуальные часовые пояса не нужны.
- На сайте нужен вход по логину и паролю.

## 3. Предлагаемые правила, ожидающие согласования

1. Общий часовой пояс — Europe/Moscow. Дедлайн задаётся датой без времени; просрочка наступает с начала следующего дня. Напоминания и сводка отправляются в 09:00.
2. Одна совместная задача имеет общий статус и общий результат. Любой назначенный исполнитель может отправить общий результат на проверку. Индивидуальная сдача каждым участником требует согласования. Завершение выполняется по правилам подтверждения результата.
3. Пользователь может добавлять соисполнителей из команды. Каждый назначенный участник видит общую карточку. Имя участника доступно для назначения, но его чужие задачи и учётные данные недоступны.
4. Администратор создаёт проекты, управляет участниками, редактирует любые задачи и назначает ответственных администраторов. При создании задачи ответственные копируются из настроек проекта; нужен минимум один ответственный администратор.
5. Только автор задачи с доступом к ней и администратор меняют название, описание, проект, дедлайн и состав исполнителей. Любой текущий исполнитель начинает работу, добавляет результат и отправляет его на проверку. Если автор исключён из исполнителей, он теряет доступ, кроме случая, когда он администратор.
6. Предлагается разрешить администратору возвращать задачу из `review` в работу с обязательной причиной. Подтверждённое правило закрытия: только администратор переводит `review` в `done`. Права определяются ролью учётной записи, а не именем пользователя.
7. Администратор заводит учётную запись и выдаёт одноразовый способ установить пароль; открытой регистрации нет. Telegram связывается с существующей учётной записью одноразовым кодом. Логин/пароль и Telegram ведут в один профиль.
8. Дополнительные уведомления о назначении и смене статуса пока не входят в обязательный объём.

## 4. Данные

| Сущность | Основные данные и ограничения |
|---|---|
| users | UUID, уникальный логин, имя, уникальный Telegram ID (может отсутствовать), роль user/admin, признак активности, дата создания. Пароль не хранится открытым текстом |
| projects | UUID, название, описание, признак архива |
| project_admins | Проект и ответственный администратор; уникальная пара |
| tasks | UUID, короткий номер, проект, автор, название, описание, important, quick, deadline_date, status, created_at, updated_at, completed_at, версия записи |
| task_assignees | Задача и исполнитель; уникальная пара; минимум один исполнитель |
| task_admins | Задача и ответственный администратор; уникальная пара |
| task_results | UUID, задача, автор результата, текст, дата создания |
| task_reviews | Задача, версия результата, проверяющий, решение, комментарий, дата; подтверждение относится только к проверенной версии результата |
| task_attachments | Задача/результат, имя, тип, размер, закрытый путь к файлу, Telegram file_id при наличии |
| task_events | Задача, действующий пользователь, событие, изменения, время; история создания, назначения, срока, статуса и результата |
| notification_deliveries | Получатель, тип, задача или дата сводки, дата отправки, состояние, попытки, ошибка, уникальный ключ защиты от повторной обработки |
| processed_updates | Telegram update_id и состояние обработки для защиты от повторного создания задач |
| bot_sessions | Пользователь, шаг формы, временные поля, срок действия; восстановление диалога после перезапуска |

Для ссылок допускается отдельный список в результате. Для создания задачи обязательны название, проект, дедлайн и минимум один исполнитель. Длина текста и лимиты вложений фиксируются при техническом проектировании до начала реализации загрузки файлов. Проекты с задачами архивируются, а не удаляются каскадно.

Время событий хранится в UTC; отображение и расчёт дня выполняются в общем часовом поясе. Дата создания не редактируется пользователем. Просрочка вычисляется по дедлайну и статусу, отдельным статусом не является. «Готово» и «Отменена» исключаются из напоминаний.

## 5. Бот

Главное меню: «Создать задачу», «Мои задачи», «На сегодня», «Просроченные», «Проекты». Для администратора добавляется «Все задачи» с фильтрами по участнику, проекту и статусу.

Создание: проект → название → описание (можно пропустить) → важная/быстрая → дедлайн → исполнители (текущий пользователь уже выбран) → предпросмотр → подтверждение. На каждом шаге доступны возврат и отмена. Запись задачи и связанных участников выполняется атомарно. Об успехе бот сообщает только после сохранения, возвращая номер и карточку.

Карточка: название, проект, описание, флаги, исполнители, ответственные администраторы, дата создания, срок, статус, результат. Действия зависят от прав: редактировать, начать, добавить результат, отправить на проверку, подтвердить результат, вернуть в работу, отменить. Пользователь отправляет задачу в `review`; кнопка подтверждения результата и переход в `done` доступны только администратору. При подтверждении сохраняются проверяющий и время выполнения (`completed_at`). Списки имеют постраничный вывод.

Отправка на проверку без текста, ссылки или файла результата блокируется с объяснением. Исполнитель не может обойти проверку кнопкой или прямым запросом. Повторное подтверждение не создаёт повторных решений. Возврат с проверки сохраняет результат и фиксируется в истории. Изменение результата требует новой проверки: старые подтверждения не засчитываются для новой версии.

Свободный текст — следующий этап: сообщение преобразуется в черновик, бот уточняет пропуски и показывает форму подтверждения. Неоднозначные даты и имена не принимаются молча. Запись без подтверждения не создаётся.

## 6. Напоминания

Серверный планировщик выбирает незавершённые задачи на текущий день и просроченные задачи. Для совместной задачи сообщение получает каждый активный исполнитель с привязанным Telegram.

Одна сводка на пользователя в день содержит только доступные ему просроченные задачи. Пустая сводка не отправляется. Перед отправкой повторно проверяются статус, дедлайн, доступ и назначение получателя. Завершённые задачи исключаются, перенос срока учитывается.

Отправки фиксируются в базе, временные ошибки повторяются с ограничением попыток. Блокировка бота пользователем отмечается как недоступность доставки. Неопределённый результат запроса Telegram может привести к повторному сообщению; абсолютная гарантия ровно одной доставки не заявляется. После перезапуска сервис восстанавливает очередь; пропущенные за текущий день напоминания обрабатываются без рассылки всей старой истории.

## 7. Архитектура и доступ

Telegram-бот, сайт и Mini App → единый серверный API на VPS → Supabase Postgres и закрытое файловое хранилище. На VPS также работает обработчик уведомлений. Конкретный язык, фреймворк и способ управления процессами выбираются перед реализацией и фиксируются отдельным техническим решением.

Доступ проверяется сервером при каждом чтении и изменении, включая вложения и действия по кнопкам. Telegram username не используется как идентификатор. Данные запуска Mini App проверяются на сервере по подписи и сроку действия; переданный клиентом ID не считается доказательством личности.

На сайте используются серверные сессии и безопасное хранение паролей в проверенном компоненте аутентификации, ограничение попыток входа и выход из сессии. Способ реализации логина без email выбирается отдельно; не предполагается, что он автоматически поддерживается выбранным провайдером.

Секреты бота и привилегированные ключи Supabase хранятся только на сервере. Для таблиц, доступных через Data API, включается RLS с проверенными политиками; ненужный прямой клиентский доступ закрывается. Привилегированный серверный доступ не заменяет проверки прав в API. Вложения выдаются только после проверки доступа.

## 8. Веб-приложение и Mini App

Единый адаптивный интерфейс: список задач, фильтры по проекту/статусу/дедлайну/флагам, создание и редактирование, карточка, загрузка результата. Администратору доступны все задачи и управление участниками/проектами. Канбан — дополнительная функция после основного списка, не условие приёмки бота.

В Telegram вход выполняется через проверенные данные Mini App после привязки профиля; на сайте — логин/пароль. Задача, созданная любым интерфейсом, доступна через остальные после обновления. Публикация требует HTTPS, адрес сайта/домен выбирается отдельно.

## 9. Этапы и приёмка

### Этап 1. База и доступ

Создан проект Supabase, схема и воспроизводимые миграции. Настроены роли, начальный администратор, тестовые данные и ограничения. Проверено: участник не читает и не меняет чужую задачу даже по известному ID; администратор видит все; исключение исполнителя закрывает доступ, если он не администратор. Авторство задачи не предоставляет право подтверждать выполнение.

### Этап 2. Бот и сервер

Пользователь создаёт задачу кнопками; данные и связи появляются в Supabase и совпадают с карточкой. Повторная доставка одного update не создаёт дубль. Совместная задача доступна всем её исполнителям и недоступна постороннему. Изменения сохраняются после перезапуска сервиса.

Исполнитель прикладывает текст, ссылку или файл и отправляет задачу в `review`. Пустой результат не принимается. Проверяется, что пользователь, включая постановщика без роли администратора, не может установить `done` через бот, сайт, Mini App или прямой запрос API. Администратор подтверждает результат и переводит задачу из `review` в `done`; проверяющий и время сохраняются. Проверяются возврат в работу и запрет подтверждения посторонним. Конфликт параллельного редактирования не приводит к молчаливой потере изменений: применяется проверка версии и предлагается обновить карточку.

В день срока приходит напоминание, со следующего дня задача входит в ежедневную сводку. Проверяются перенос срока, завершение перед отправкой, отмена, смена исполнителя, блокировка бота и перезапуск обработчика.

### Этап 3. Веб и Mini App

Вход обоими способами ведёт к одному пользователю. Проверены права через интерфейс и прямые запросы API, создание и результат через оба интерфейса, открытие Mini App из бота и сайта в мобильном/настольном браузере.

### Этап 4. Развёртывание

Настроены HTTPS, автоматический запуск после перезагрузки VPS, журнал ошибок без секретов, резервное копирование базы и файлов с проверкой восстановления. Переданы инструкция развёртывания, управление пользователями и порядок восстановления. Политика хранения копий и целевое время восстановления согласуются до запуска для команды.

## 10. Вне первой версии

Голосовые задачи, ИИ-разбор сообщений, наблюдатели, общий групповой чат, зависимости и подзадачи, повторяющиеся задачи, учёт времени, календарные интеграции, дополнительные каналы уведомлений. Комментарии можно добавить отдельно; обязательный результат и история изменений входят в основу.

## 11. Вопросы для согласования

1. Можно ли любому исполнителю отправить общий результат на проверку за всех, или каждый должен сдавать свою часть?
2. Может ли пользователь сам назначать коллег? Кто назначает ответственных администраторов: пользователь или настройки проекта?
3. Подходят ли дата дедлайна без времени, общий часовой пояс Москвы и отправка в 09:00?
4. Подходит ли создание учётных записей администратором с последующей привязкой Telegram?
